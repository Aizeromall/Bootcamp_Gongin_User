# 회원정보 및 종목별 삭제·복구 백엔드 1차 구현

작업자: 최현준 / 작업일: 2026-10-29

## 범위와 상태

백엔드 및 후속 승인된 회원정보 화면의 연결 계약입니다. 실제 DB 쓰기·스키마 변경·자동 정리 실행·스케줄 등록은 하지 않았습니다.
2026-10-29 후속 승인으로 MY 프로필 카드 → 회원정보 수정 화면과 삭제 안내 Dialog를 연결했습니다.
일반/간편로그인의 복구 대상 응답은 로그인 화면의 복구 확인 Dialog(예/아니오)에서 처리합니다.

실제 customer 컬럼은 `c_deletdate`입니다. `c_deletedate`라는 새 컬럼을 만들지 않습니다.
조회한 DB는 c_id_seq VARCHAR(50), 이름(50), 주소(255), 전화번호(20), 성별(10),
가입/삭제일 DATETIME 구조입니다. customer를 참조하는 여러 FK가 NO ACTION입니다.

## 승인받은 프로세스

1. 최초 가입 또는 종목 추가: 고정 suffix `_01` 축구 / `_02` 농구 / `_03` 야구 / `_04` 배구.
   `c_signupdate`는 해당 종목 선택 시점(KST), 신규 종목 레이팅은 1500, 팀은 무소속입니다.
   기존 계정에서 신규 종목은 공통 개인정보·로그인 방식·저장 비밀번호 해시를 복사합니다.
   c_category는 직접 부여하지 않고 기존 팀 가입/생성 흐름을 유지합니다.
2. 종목 삭제 신청: 그 행의 c_deletdate만 현재 KST로 기록합니다. 전체 신청은 활성 행만 변경합니다.
   반복 신청으로 기존 날짜를 연장하지 않으며, 한 종목을 지워도 다른 활성 종목은 유지됩니다.
3. `현재 시각 < 삭제 신청일 + 30일`인 동안에만 복구 가능합니다. 정확히 30일이면 만료입니다.
   복구는 c_deletdate를 NULL로 되돌리며 선택일·등급·팀·이력은 초기화하지 않습니다.
4. 모든 종목에 삭제일이 있으면 계정 삭제 대상일은 **가장 늦은 삭제일 + 30일**입니다.
   하나라도 복구하면 전체 계정 삭제 대상에서 빠집니다. 종목별 기간 경과 상태와
   실제 customer 행 DELETE 여부는 구분합니다.
5. 30일 경과 종목의 물리 삭제는 아래 FK 안전 정리 도구가 처리합니다. 기존 참조가 남으면 blocked입니다.
   만료 행의 같은 PK를 덮어써 새 가입처럼 만들지 않습니다. 삭제 완료된 PK에만 신규 행을 생성합니다.

## API 및 Swagger 검사 순서

FastAPI 재시작 후 `/docs`의 **Auth Account** 그룹에서 확인합니다.
이 문서의 쓰기 요청은 운영 DB의 Try it out으로 검증하지 마세요. 자동 검사는 mock DB로만 실행했습니다.

| 경로 | 역할 | 인증 |
| --- | --- | --- |
| GET `/auth/account` | 개인정보·종목별 active/recoverable/expired·계정 삭제 대상일 조회 | 서비스 JWT |
| PATCH `/auth/account/profile` | 개인정보·비밀번호·선호 종목 최종 선택·포지션 일괄 수정 | 서비스 JWT |
| POST `/auth/account/sports` | 신규 종목 가입, 201 | 서비스 JWT |
| DELETE `/auth/account/sports/{sport}` | 한 종목 삭제 신청 | 서비스 JWT |
| POST `/auth/account/withdraw` | 활성 종목 전체 삭제 신청 | 서비스 JWT |
| POST `/auth/account/sports/{sport}/restore` | 활성 계정에서 유예 종목 복구 | 서비스 JWT |
| GET `/auth/account/recovery` | 전 종목 비활성 계정 복구 확인 | 복구 전용 JWT |
| POST `/auth/account/recovery/restore` | 확인 후 선택 종목 복구 | 복구 전용 JWT |

프로필 요청 예시:

```json
{"c_name":"회원 이름","c_phone":"01012345678","c_position":{"1":"MF","4":"세터"}}
```

수정 허용 항목은 이름·주소·전화번호·성별·생년월일·활성 종목 포지션입니다.
일반 가입자 비밀번호 변경은 c_pw/current_password를 함께 전달하며 현재 비밀번호를 검증합니다.
비밀번호 해시는 조회 응답에 포함하지 않습니다. 소셜 회원은 비밀번호를 생성/변경할 수 없습니다.
ID·종목별 PK·팀/가입 상태·등급·로그인 방식·가입일·삭제일은 임의 직접 수정이 불가능합니다.
종목 변경은 프로필의 `preferred_stocks`에 최종 선택 목록, `c_position`에 선택 종목 전체의 포지션을 보내
개인정보와 함께 하나의 트랜잭션으로 저장합니다. 기존 개별 추가/삭제 신청/복구 API도 유지합니다.
추가 종목은 고정 suffix 신규 행, 빠진 활성 종목은 삭제일 기록, 선택된 유예 종목은 삭제일 NULL 복구입니다.
변경하지 않은 행의 가입일/삭제일은 유지합니다. 빈 선택 목록은 전체 종목 삭제 신청이며 로그아웃 대상입니다.

```json
{"preferred_stocks":[1,4],"c_position":{"1":"FW","4":"세터"}}
```

종목 추가 요청:

```json
{"sport":4,"c_position":"세터"}
```

복구 확인 예 요청:

```json
{"sports":[1,4]}
```

HTTP 401은 인증 누락/실패, 403은 비활성·복구 기간 경과, 404는 없는 계정/종목,
409는 중복·상태/FK 충돌, 422는 입력 검증, 500은 DB 오류, 503은 JWT 설정 오류입니다.
각 API에 Swagger 응답 설명을 등록했습니다. 원문 SQL·비밀번호·비밀키는 응답하지 않습니다.

## 로그인과 프론트 연결 계약

- 활성 종목이 하나 이상이면 기존 access_token 응답을 유지하며 active 종목만 member_ids/preferred_stocks에 포함합니다.
- 전 종목 비활성 계정은 일반 비밀번호 또는 Google/Kakao/Naver 공급자 인증 후
  `result=RECOVERY_REQUIRED`, `recovery_required=true`, `recovery_token`, 종목 상태를 반환합니다.
  **access_token은 발급하지 않습니다.** 일반 JWT와 다른 audience, 10분 만료의 복구 JWT입니다.
- Swagger Authorize에는 이 경우 recovery_token을 넣어 복구 API만 검사합니다.
  복구 JWT는 서비스/채팅 인증으로 사용할 수 없으며 서비스 JWT로 복구 전용 API에 접근할 수도 없습니다.
- 복구 토큰의 계정·공급자·현재 DB 스냅샷을 검증합니다. 복구/재삭제/비밀번호 변경 등 상태 변경 후에는
  토큰을 다시 얻어야 합니다. 별도 토큰 폐기 테이블이나 refresh token은 추가하지 않았습니다.
- 프론트는 recovery_required를 먼저 분기해 복구 확인 화면으로 이동해야 합니다.
  ‘예’는 선택한 유예 종목으로 restore 요청, ‘아니오’는 토큰 폐기 후 로그인 화면 복귀입니다.
- 변경 API의 `session`은 재발급된 인증 결과입니다. 마지막 종목 삭제 시에는 복구 전용 결과이므로
  일반 세션에 그대로 저장하지 않아야 합니다. 다른 종목이 활성이라면 새 서비스 JWT로 교체합니다.
- 만료된 종목은 복구되지 않습니다. 모든 종목이 만료되면 로그인은 403으로 차단됩니다.
- 후속 프론트는 로그인 시 복구 확인 Dialog에서 복구 가능한 종목 전체를 안내하며,
  예 선택 시에만 복구 요청을 보냅니다. 회원정보 화면에도 4개 종목 선택을 표시하고,
  기존 활성 종목은 선택된 상태로 초기화합니다. 선택 해제는 저장 전 안내 확인을 거칩니다.
- Firebase Authentication 가이드를 참고해 공급자 ID 토큰/서비스 JWT/FCM 토큰/복구 JWT를 구분했습니다.
  Firebase 계정 삭제나 공급자 연결 해제는 하지 않습니다.

## 30일 정리 도구 — 기본 읽기 전용

```sh
python3 -m python.FastAPI.auth.account_retention
```

`--limit` 기본 100, 최대 1000입니다. next_cursor가 있으면 `--after`로 다음 배치를 확인합니다.
정보 스키마에서 실제 customer FK를 읽어 참조가 하나라도 있는 종목은 blocked 목록에 남깁니다.
CASCADE FK도 이력을 임의 삭제하지 않도록 동일하게 차단합니다. 동적 식별자는 인용하고 값은 바인딩합니다.

실제 DELETE는 별도 `--delete` 옵션이 있어야 실행됩니다. 작성 중 이 옵션을 실제 DB에 실행하지 않았습니다.
주기적 운영을 위해서는 별도 스케줄러에서 전체 배치를 순회하도록 등록해야 합니다.
서버 시작이나 Swagger 조회만으로 자동 DELETE를 시작하지 않습니다. 운영 스케줄도 미등록 상태입니다.

**중요: 현 DB 구조에서 기존 이력이 있는 회원은 30일이 지나도 물리 삭제가 막힙니다.**
예약·결제·문의·게시글·채팅·팀·신고·제재·출석·알림 등 보존/익명화/삭제 정책을 먼저 정해야 합니다.
FK 검사를 끄거나 연관 행을 연쇄 삭제하는 코드는 넣지 않았습니다. 이런 종목 재선택은 409로 막습니다.
완전한 자동 영구 삭제 및 FK 이력이 있는 종목 재가입은 아직 완료 조건을 충족하지 않습니다.

## 활동 차단 및 추가 결정 필요 사항

- 이 신규 API와 로그인은 종목 활성 상태를 검사합니다. 기존 채팅·알림도 활성 회원 조건을 사용합니다.
- 하지만 기존 예약/결제/게시판/팀 등의 일부 API는 JWT 인증이나 c_deletdate 조건 없이 회원 ID만 확인합니다.
  전체 시스템에서 탈퇴 종목의 모든 활동 차단을 보장하려면 해당 API들에 대한 후속 보강이 필요합니다.
- 기존 예약의 취소/환불, 팀장 위임, 게시글·채팅 기록 삭제는 이번 종목 삭제 신청에 연쇄 실행하지 않습니다.
- 복구 시 서비스/채팅의 기존 유효 토큰을 전역 폐기하는 세션 버전 기능은 기존 스키마에 없습니다.
  전역 강제 로그아웃·권한 체계 통합은 후속 설계 사항입니다.
- 위 사항은 개인정보/FK 관계 보존과 다른 회원 영향이 있어 임의로 결정하지 않았습니다.
